# Фильтр учебных приоритетов

Это не замена отдельному roadmap. Это фильтр для всей исходной папки `Materials`: что действительно приближает к frontend-работе, а что пока создаёт лишнюю нагрузку.

## Исходная позиция

Уже можно опираться на:

- уверенную HTML/CSS-вёрстку;
- адаптивность и перенос макета из Figma;
- визуальную насмотренность;
- опыт реальных задач и коммуникации;
- способность читать код и примерно видеть, где что происходит.

Нельзя пока считать устойчивыми:

- написание JavaScript с чистого листа;
- синтаксис без постоянной подсказки;
- mental model асинхронности;
- TypeScript как систему типов, а не набор `interface`;
- React за пределами базовых `useState` и `useRef`;
- самостоятельную декомпозицию data-heavy интерфейса.

## P0: активное ядро

### 1. JavaScript как язык

Нужно не перечитать все методы, а уметь ими пользоваться:

- значения, типы, преобразования, `===`, truthy/falsy, `null`/`undefined`;
- переменные, область видимости, hoisting, замыкания;
- функции, параметры, callbacks, `this`;
- массивы и объекты по ссылке, копирование и иммутабельные обновления;
- условия, циклы и методы массивов как разные инструменты;
- ошибки, `throw`, `try/catch/finally`;
- прототипная модель на уровне, достаточном для чтения кода и собеседования.

Часть синтаксиса уже есть в приложении. Активная работа должна идти через задачи, а не через переписывание карточек.

### 2. Асинхронность и браузер

- call stack, task/microtask и event loop;
- Promise и цепочки;
- `async/await` как синтаксис над Promise, а не способ «сделать функцию быстрой»;
- `fetch`, проверка `response.ok`, JSON, HTTP-статусы и
  [REST/API-flow](../02-javascript/rest-api-for-frontend.md);
- race condition, отмена и устаревший ответ;
- DOM, события, bubbling/delegation, `target`/`currentTarget`;
- формы и `FormData`.

### 3. TypeScript поверх понятного JavaScript

- inference и аннотации;
- `type`/`interface`;
- union, literal types, narrowing;
- `unknown` вместо бездумного `any`;
- функции, объекты, массивы, события и API-ответы;
- generics и базовые utility types;
- строгая типизация React props/state/events.

### 4. React core

- компонент, props, state и render;
- snapshot состояния и очередь обновлений;
- controlled inputs;
- условный рендеринг, списки и устойчивые `key`;
- lifting state up;
- `useEffect` и cleanup;
- `useReducer`, context и custom hooks;
- понимание причины перерендера.

## P1: рабочий frontend

- React Router;
- загрузка server state, loading/error/empty/success;
- TanStack Query или RTK Query после ручного понимания базового fetch-flow;
- формы и валидация;
- Redux Toolkit — когда появляется действительно общее сложное client state;
- доступность: клавиатура, focus, dialog, labels, ошибки формы;
- тесты поведения с Testing Library;
- Git-ветки, небольшие коммиты, review;
- минимальный CI: typecheck, lint, tests и production build;
- REST/API-контракт, auth-flow на уровне клиента;
- базовая безопасность: XSS, CSRF, безопасное хранение сессии;
- browser rendering, bundle analysis и осмысленный code splitting.

## P2: после одного законченного React + TypeScript проекта

- Next.js;
- Storybook и дизайн-система;
- WebSocket;
- Canvas/WebGL, если нужны конкретному проекту;
- сложные оптимизации React;
- Feature-Sliced Design как один из вариантов организации, а не обязательная истина;
- Docker и более сложная CI/CD/deployment-инфраструктура;
- GraphQL, если он появляется в вакансии или проекте.

## Later: осознанно не сейчас

- глубокий Node.js/Fastify/NestJS;
- проектирование базы данных;
- сложная JWT/refresh-token инфраструктура на сервере;
- микросервисы и микрофронтенды;
- Kubernetes;
- глубокое администрирование Linux;
- Python-материалы;
- изучение Angular/Vue «на всякий случай».

Для текущего трека достаточно понимать границу frontend/backend, HTTP, API-контракт, cookies/tokens и уметь интегрироваться с готовым сервером.

## Рекомендуемая последовательность циклов

### Цикл A — уверенный JS

Результат: несколько маленьких задач без React, где есть коллекции данных, функции, DOM, события, запрос и обработка ошибки.

### Цикл B — TypeScript

Результат: те же модели и функции типизированы без `any`; внешние данные сначала считаются `unknown` и проверяются.

### Цикл C — React

Результат: приложение с формой, списком, фильтрами, состояниями загрузки и маршрутизацией.

### Цикл D — рабочее качество

Результат: тесты ключевых сценариев, доступная модалка/форма, безопасный вывод, обработка race condition, понятная архитектура.

### Цикл E — портфолио и собеседование

Результат: законченный проект, README с решениями и trade-offs, короткие устные ответы, live-coding без копирования готового решения.

## Что не является прогрессом само по себе

- сохранить ещё один курс;
- посмотреть видео без кода;
- прочитать всю книгу перед первой задачей;
- скопировать сложный fetch/cache слой, не умея объяснить Promise;
- подключить Redux, Next.js или FSD ради строки в резюме;
- получить от AI готовый проект, который нельзя восстановить частями;
- заучить ответы без отладки реальных ошибок.

## Ограничитель текущего фокуса

До устойчивого выполнения циклов A–C новый большой технологический трек добавляется только при прямой необходимости проекта или вакансии. Любой новый материал сначала проходит фильтр из [`README.md`](../README.md#правило-против-нового-информационного-склада).
